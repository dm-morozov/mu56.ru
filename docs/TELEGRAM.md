# Уведомления владельцу о заявках

Готова отправка в личный Telegram-чат владельца через [официальный Bot API](https://core.telegram.org/bots/api#sendmessage). Клиентский бот, ответы клиентам и Google Calendar — отдельный этап.

## Подключение локально

1. Создать **отдельного** бота в [@BotFather](https://t.me/BotFather): `/newbot`, название и свободный username с окончанием `bot`. Токен не присылать в чат и не добавлять в frontend.
2. Из PowerShell в корне проекта запустить:

```powershell
.\scripts\dev_telegram.ps1 Configure
```

Ввод токена скрыт. Мастер проверит бота и покажет ссылку на него с одноразовой меткой. Откройте её **своим** Telegram-аккаунтом, нажмите START, вернитесь в терминал и нажмите Enter. Проверка ждёт сообщение до 5 секунд; если оно ещё не дошло, можно повторить проверку с той же ссылкой без повторного ввода токена. Если START-кнопки нет, мастер покажет точную команду /start с меткой для отправки боту. q отменяет настройку без сохранения. Мастер найдёт только личный чат с этой меткой и попросит подтвердить получателя. Он не выбирает первый попавшийся чат. Telegram username владельца не заменяет числовой private chat ID.

Настройка сохраняется в `.local/telegram.json`, который исключён из Git. Django читает его только в DEBUG. При существующем webhook мастер останавливается и не меняет его. Если бот уже занят другим приложением, используйте нового бота. Опция `ConfigureExisting` позволяет ввести заранее известный ID своего личного чата без чтения обновлений; получатель показывается для подтверждения.

3. Перезапустить Django, чтобы сервер увидел настройку. Отдельные команды при каждом запуске читают актуальный файл.
4. Отправить **одно** тестовое сообщение без данных клиентов:

```powershell
.\scripts\dev_telegram.ps1 Test
```

Проверить, что оно появилось в Telegram. Подтверждение API означает отправку, но не прочтение владельцем.

5. В отдельном терминале запустить обработчик:

```powershell
.\scripts\dev_telegram.ps1 Worker
```

Терминал должен оставаться работающим. `Once` обрабатывает только текущие готовые задания; отложенные задачи надо обработать следующим запуском. После этого отправить тестовую заявку через сайт и проверить сообщение, заявку в Django admin и статус «Отправлено». При необходимости удалить тестовую заявку вручную из админки. Старые заявки, созданные до подключения очереди, автоматически не отправляются.

На восстановленной базе используйте `telegram_worker --created-after <ISO-время-с-часовым-поясом>`, чтобы исключить старые ожидающие записи. Фильтр ограничивает отправку датой создания заявки и не удаляет старые записи. Для мобильного preview 3001 worker должен работать с той же отдельной базой, что backend 8002. 6 октября добавлен фильтр; 17 тестов уведомлений проходят с подменённым Telegram API. Реальная отправка новой заявки пока не выполнена: автоматическая проверка запуска worker отклонила передачу персональных данных и потребовала явного подтверждения пользователем содержимого и настроенного получателя Telegram.

Позднее 6 октября владелец явно подтвердил отправку этой и следующих заявок с заполненными сведениями в настроенный личный Telegram-чат. После подтверждения worker запущен для базы мобильного preview с порогом `2026-10-06T16:12:00+00:00`. Telegram API подтвердил отправку новой заявки (статус sent, одна попытка, сохранён message_id, время 16:19:01 UTC). Старая ожидающая запись из восстановления осталась pending с нулём попыток. Это локальный постоянно работающий процесс; после его остановки или перезагрузки компьютера запуск необходимо повторить. Автозапуск Windows этой проверкой не настроен.

## Что приходит

Номер заявки, имя и телефон, предпочтительный способ связи, дата и время в Оренбурге, выбранные программа/герой/дополнения, возраст, количество детей, место и пожелания — если поля заполнены. Состав и известный предварительный расчёт берутся из снимка на момент заявки, а не из изменившихся тарифов. Цена не объявляется окончательной; выезд и состав надо согласовать. Внутренние заметки менеджера и текст согласия не отправляются.

Сообщение обычным текстом, без интерпретации HTML клиента и предпросмотра ссылок. Ограничена длина, включая эмодзи. Bot API возвращает ID сообщения; он записывается в админке вместе с временем отправки.

## Очередь и ошибки

Заявка и одно уведомление сохраняются **одной транзакцией**. В HTTP-запросе сайта нет обращения к Telegram: скорость и успех сохранения не зависят от мессенджера. Очередь находится в PostgreSQL, поэтому переживает перезапуск приложения. Процесс `telegram_worker` забирает задания с блокировкой; несколько обработчиков не отправляют одно активное задание одновременно.

- Telegram 429: повтор после `retry_after` или более длинной задержки. Ответ 5xx: отложенный повтор. До пяти попыток, затем требуется действие менеджера.
- 400/401/403: ошибка, нужна проверка настройки/доступа и ручной повтор.
- Обрыв сети, некорректный ответ или прерванный обработчик: «Доставка не подтверждена». Перед повтором проверить чат, потому что сообщение могло быть доставлено. Bot API не предоставляет ключ идемпотентности для sendMessage: абсолютная гарантия отсутствия дублей при таком обрыве невозможна.

В админке заявки видно состояние, число попыток, причину, время и ID сообщения. Выделите нужные заявки в списке и выберите «Повторить неудачные уведомления (сначала проверьте Telegram)». Повторяются только ошибки и неопределённые доставки; отправленные/активные/обычные ожидающие не сбрасываются. Действие требует права изменения заявки. Ошибки сохраняются в безопасном виде: без токена, URL запроса и удалённого описания.

При выключенном Telegram новые уведомления остаются в очереди. Включение и запуск обработчика отправят ожидающие заявки — учитывайте это при использовании тестовых данных.

## После развёртывания

Задать `TELEGRAM_ENABLED=1`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` в окружении Django и обработчика. Локальный JSON в production не читается. ID — положительное число личного чата владельца. Запустить `python backend/manage.py telegram_worker` отдельным сервисом с автоперезапуском, теми же настройками БД и мониторингом очереди. Bot API запрашивается по HTTPS с таймаутом 10 секунд, перенаправления запрещены.

Миграция leads/0002 создаёт таблицу уведомлений и не отправляет ничего сама. Проверки: `python backend/manage.py test leads catalog --noinput` с окружением PostgreSQL. Автотесты используют подмену Telegram transport, поэтому сообщения наружу не отправляют.
