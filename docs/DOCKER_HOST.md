# Docker на сервере для нескольких проектов

## Проверено на первом VPS

Selectel `web-vds-01`, Москва, Ubuntu 24.04.4 LTS, 1 vCPU,
2 ГБ RAM, диск 25 ГБ. Swap 2 ГиБ подключён, fstab проверен;
проверка после реальной перезагрузки ещё остаётся.

Установлены Docker Engine 29.8.2, Compose 5.6.0, Buildx 0.37.1
из официального apt-репозитория Docker. Docker включён при загрузке;
`systemctl is-active docker` вернул active. Тест `docker run --rm hello-world`
прошёл. Этот тест не проверяет приложение или восстановление данных.

Конфигурация [docker-daemon.json](../deploy/docker-daemon.json) проверена
`dockerd --validate` и установлена только после подтверждения отсутствия
предыдущей конфигурации/контейнеров. Журналы используют local driver:
10 МБ × 3 файла на контейнер. `live-restore` включён; это не замена репетиции
обновления и не обещание сохранения процессов при любых обновлениях Docker.

Созданы приватные каталоги `/srv/projects` и `/srv/projects/mu56` (0700).
Docker API не открыт по TCP. Управление Docker пока через root по проектному
SSH-ключу; создан ограниченный mu56-deploy с командой status. Обновление и
откат этому пользователю пока не разрешены: [DEPLOY_ACCESS.md](DEPLOY_ACCESS.md).
Членство в группе docker фактически даёт права root, поэтому не добавлять
туда пользователей автоматически. При первичной проверке был открыт только SSH; актуальный статус размещения ниже.

После установки около 21 ГБ свободного диска, около 1.6 ГиБ доступной RAM,
swap не используется. Это замер пустого сервера, не оценка нагрузки сайта.

## План контейнерного размещения

- Один Compose-проект на сайт: `mu56-staging` и отдельный проект диплома.
  Постоянные данные отделены от образов и каталогов релизов.
- Django/Gunicorn, Next.js, PostgreSQL и Telegram worker — отдельные службы.
  Worker первоначально выключен. Next.js не получает секреты backend.
- Общий вход HTTPS маршрутизирует домены; для каждого сайта отдельная сеть
  связи с входным proxy. Базы доступны только в приватной сети своего проекта.
  Не объединять все приложения и базы одной общей сетью.
- Не публиковать PostgreSQL, Gunicorn и Next.js на 0.0.0.0. Наружу только
  согласованные SSH и HTTPS/HTTP входного proxy. Docker-публикация портов
  может обходить UFW, поэтому полагаться только на UFW недостаточно.
- Лимиты RAM/CPU и ротация журналов; ограничения файлов дипломного хранилища.
  Сумму лимитов уточнить замерами и оставить ресурсы ОС.
- Собирать образы вне малого VPS, сохранять привязку к полному SHA и digest.
  Обновления Docker/базовых образов выполнять после проверки; не менять
  теги latest произвольно при рабочей выкладке.
- Перед обновлением резерв БД/media, предыдущие образы и запись релиза.
  Откат кода не откатывает схему БД. Не использовать `compose down -v`
  или глобальный prune для обычного обновления сайта.
- Резерв данных вне VPS, контроль диска, памяти/OOM, swap и срока сертификата.
  Назначение и хранение резервов согласовать отдельно.

## Размещение 7 октября 2026

Приложение работает на https://dev.mu56.ru в одном Compose-проекте `mu56`.
DNS проверен; mu56.ru/www остаются на GitHub Pages. Nginx принимает 80/443,
HTTPS имеет действующий сертификат Let's Encrypt; тест продления и reload hook
прошёл. UFW включён: разрешены 22/80/443, PostgreSQL/приложения не публикуются.
Доступ dev ограничен текущим публичным IP владельца, остальные получают 403.
Присутствуют noindex, запрет robots и пустой sitemap.

Образы собраны локально из чистого снимка cc60bd9 и добавленной Docker-конфигурации,
проверены до передачи на VPS. Чужие незавершённые редакционные правки не включены.
Каталог: 162 записи, 27 фотографий; клиентские заявки и пользователи не переносились.
Восстановление отсутствующих архивных фото для экспорта выполнено только в приватной
временной папке; скрытые персонажи не опубликованы.

12 HTTPS GET-проверок прошли. Тестовая заявка с CSRF сохранилась (201), серверная
цена анимации с азотным шоу — 7400; запись затем удалена, заявок и очереди 0.
Две исходные фотографии и их Next-оптимизированные варианты вернули 200.
PostgreSQL-приложение не имеет SUPERUSER/CREATEDB/CREATEROLE.
Telegram выключен. Django check --deploy оставляет только намеренные предупреждения
HSTS includeSubDomains/preload: основной домен ещё не перенесён.

После запуска без нагрузки: контейнеры около 187 МиБ, доступно около 1.4 ГиБ RAM,
18 ГБ диска, swap почти не используется. Это не нагрузочное испытание.
Инструкция: [DOCKER_DEPLOY.md](DOCKER_DEPLOY.md).
