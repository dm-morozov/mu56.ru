# Первый тестовый сервер

## Текущий статус — 6 октября 2026

Сервера у владельца пока нет. Ветка `local/release-20261006` опубликована;
CI коммита `786448d3a1699f1540913602f44ca72971ac211e`
[прошёл](https://github.com/dm-morozov/mu56.ru/actions/runs/37523060101).
Старый main, GitHub Pages и основной домен не переключались.

## Что определить до покупки

- Ежемесячный бюджет на VPS и отдельное хранение резервов.
- Тестовый адрес: например, отдельный поддомен, точное имя согласовать.
- Ограничение доступа к тестовому адресу: разрешённые IP или другой
  согласованный способ. Noindex сам по себе не ограничивает доступ.
- Где хранить внешние копии и кто получает сообщения об ошибках резервирования.

После выбора провайдера проверить актуальные тарифы, доступные ресурсы и
runtime. Для первичного подбора ориентироваться на [HOSTING_READINESS.md](HOSTING_READINESS.md);
не считать CI или локальный Docker нагрузочным тестом будущего VPS.

## Подготовка тестовой площадки

1. Создать отдельный Linux-сервер и проектный SSH-доступ. Владелец вводит
   ключи/секреты локально; они не попадают в Git или переписку.
2. Установить runtime из [DEPLOYMENT.md](DEPLOYMENT.md), создать пользователя
   приложения и отдельную PostgreSQL-базу с ограниченной ролью. Публичны только
   SSH по согласованным правилам и Nginx; порты приложения/БД закрыты.
3. Выбрать полный SHA с успешным CI. Скачать этот релиз в отдельный каталог,
   установить Linux-зависимости, восстановить только каталог и его media.
   Клиентские заявки, локальная очередь и секреты не переносятся автоматически.
4. Подготовить отдельные environment-файлы: `SITE_URL` — тестовый HTTPS-адрес,
   `SITE_INDEXING_ENABLED=false`, Telegram сначала выключен. Для Django
   согласовать `DJANGO_ALLOWED_HOSTS` и `DJANGO_CSRF_TRUSTED_ORIGINS`.
5. Шаблон Nginx сейчас содержит **mu56.ru**. Для staging подготовить отдельную
   копию: заменить server_name, проверки Host, HTTPS redirect, пути сертификата
   и внутренний Host на тестовый домен; согласовать ограничение доступа.
   Не устанавливать шаблон без этих изменений и не менять основной DNS.
6. Получить сертификат тестового адреса, проверить конфигурацию и его
   автоматическое продление. Настроить systemd и постоянные каталоги;
   выполнить migrate/collectstatic и preflight по инструкции первого запуска.
7. Собрать Next.js с тестовым окружением и внутренним API. Запустить backend
   и frontend; worker остаётся выключен до согласованной проверки уведомлений.

## Проверка доступности после запуска

Из разрешённой сети, с действительным доверенным сертификатом:

```powershell
.\.venv\Scripts\python.exe scripts/check_staging.py https://TEST_HOST --report .local/staging/http-check.json
```

`TEST_HOST` заменить согласованным адресом. Скрипт выполняет только GET:
8 страниц, robots, sitemap и 2 API каталога. Проверяет прямой HTTP 200,
наличие H1/noindex, закрытый wildcard robots, пустую sitemap и непустой
каталог. TLS проверяет стандартный клиент Python; ошибки сертификата не
игнорируются. Отчёт не сохраняет HTML, контакты или ответы API.

Для локальной проверки допускается `--allow-http`; такой результат не
подтверждает HTTPS. Скрипт не отправляет заявки и не проверяет цены,
фотографии, аналитику, уведомления или работоспособность systemd.
При ограничении адреса по IP выполнять его из разрешённой сети; редирект
на страницу входа не считается успешной проверкой сайта.

## Приёмка и репетиция отката

- На настоящем телефоне проверить фото, меню, поиск, выбор состава и маску.
- Согласованно отправить одну вымышленную заявку, сверить цену/состав/согласие
  в админке. Реальную доставку владельцу проверять отдельным согласованным
  шагом; после проверки обработать тестовую очередь перед рабочим запуском.
- Проверить перезагрузку сервера, восстановление резервной копии в отдельную
  базу и получение сигнала о сбое резервирования.
- Для репетиции подготовить второй совместимый релиз. До переключения
  сохранить предыдущий SHA, каталог и статику; общий static не очищать так,
  чтобы предыдущий релиз потерял свои файлы. Остановить worker, переключить
  current атомарно, перезапустить службы, повторить HTTP/форму.
- Вернуть предыдущий каталог кода и повторить проверки. Откат кода не
  откатывает БД: миграции и сохранённые после резерва заявки требуют отдельного
  решения. При несовместимой схеме простой возврат current не допускается.
- Записать проверенные SHA, результаты и время. Только затем согласовать
  подключение основного домена, рабочий Telegram и включение индексации.

Автоматический deployment workflow появится после подтверждения адреса,
доступа и успешной серверной репетиции. Сейчас готов CI, а не действующий CD.
