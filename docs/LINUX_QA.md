# Полная локальная репетиция Linux-запуска

Стенд `deploy/qa/` использует установленный Docker Desktop. Это проверка приложения до покупки сервера, а не замена production-служб systemd. Образы и контейнеры остаются локальными, публикации в registry нет.

Ubuntu 24.04: Python 3.12, Node 24.18.0, pnpm 11.19.0, Nginx и клиент PostgreSQL 18. Отдельный контейнер PostgreSQL 18; его порт не опубликован. Backend/Next.js слушают loopback внутри Ubuntu, Nginx — единственный опубликованный вход `127.0.0.1:18444`. Используется настоящий deploy/nginx/mu56.conf и Gunicorn-конфигурация проекта, временный самоподписанный сертификат.

Для приложения создаётся отдельная роль PostgreSQL без superuser/CREATEDB/CREATEROLE. Миграции/импорт/Gunicorn/Next выполняются от пользователя mu56; Next получает отдельное окружение без пароля БД/ключа Django/токена Telegram. Worker не запускается, токен пустой, TELEGRAM_ENABLED=0. В тестовую базу переносится только каталог и привязанные фотографии; одна проверочная заявка создаётся с вымышленным телефоном.

## Повторить на Windows

Docker Desktop должен быть запущен. В PowerShell из корня:

```powershell
.\scripts\check_linux_stack.ps1
```

Скрипт находит docker.exe даже вне PATH, загружает локальные параметры PostgreSQL, экспортирует свежий каталог в уникальную `.local/mu56-linux-qa-…`, собирает Linux-образ и запускает новый Compose-проект с новой базой. Первичная загрузка образов и зависимостей требует сети и свободного места. Успешный итог — `report/linux-stack.json` с `verified: true`.

Проверяет production build, серверный HTML основных страниц, локальный noindex/robots, админку/статику, фото из импорта и оптимизацию WebP на Linux, CSRF/Origin, сохранение новогодней заявки с азотным шоу за 12400 ₽, ограниченную роль БД, отсутствие backend-секретов в Next, полную копию данных и восстановление её в отдельную базу, сохранность заявки/фото после перезапуска приложения.

Контейнеры/сеть этого запуска останавливаются и удаляются в finally. Volume базы остаётся для осмотра; скрипт не использует `down -v`, глобальный prune или очистку чужих проектов. Приложение на 3000/8000 и действующий mu56.ru не переключаются. Повторный запуск создаёт новый проект, а не переиспользует предыдущую базу. Для удаления накопленных QA-volumes сначала отдельно проверить их имена и необходимость сохранения.

Build context ограничен Dockerfile.dockerignore: backend/frontend/deploy и один скрипт проверки; .local, ai-context, .git, исходный архив владельца, Windows-зависимости/сборки, заполненные env, ключи и сертификаты не включаются. [Правила Docker build context](https://docs.docker.com/build/concepts/context/). Клиент PostgreSQL в Ubuntu устанавливается из [официального PGDG](https://www.postgresql.org/download/linux/ubuntu/).

## Ограничения

Стенд не проверяет запуск systemd, его sandbox/таймер, firewall реального сервера, Let's Encrypt/продление, доставку настоящему Telegram-получателю, внешний носитель/шифрование, DNS или индексацию. Синтаксис systemd проверен отдельным check_deploy_linux.py. Самоподписанный TLS в стенде проверяет маршрутизацию/secure cookie; это не проверка публичного сертификата. Производительность контейнера на рабочем компьютере не определяет ресурсы Selectel.

Статус конкретной репетиции и фактические версии записываются в docs/STATUS.md после получения успешного отчёта. Наличие Dockerfile или успешная сборка образа сами по себе не означают, что проверка сайта прошла.

## Результат 5 октября 2026

`scripts/check_linux_stack.ps1` прошёл полностью: 33 проверки, production build и TypeScript. Отчёт `.local/mu56-linux-qa-afb3de0f4b/report/linux-stack.json`: Python 3.12.3, Node 24.18.0, PostgreSQL 18.6. Импортированы 157 записей и 27 фото. Полный Linux-дамп восстановлен в отдельную `mu56_restore_qa`, количества строк всех 22 таблиц совпали. Метаданные копии сохранены в `report/data-backup-manifest.json`; сам временный дамп был внутри удалённого QA-контейнера. Volume с исходной и восстановленной базами оставлен.

Первый запуск собрал приложение, но остановился на проверке `/proc` от другого UID: Docker root не имеет CAP_SYS_PTRACE. Проверка теперь читает окружение от того же непривилегированного пользователя. Также выявлен служебный control socket Gunicorn 26, пытавшийся писать в HOME: в общей production-конфигурации установлен `control_socket_disable=True`, управление процессами остаётся у systemd. [Описание настройки Gunicorn](https://gunicorn.org/reference/settings/#control-socket-disable). Повторный запуск в новом проекте прошёл; успешные результаты первого запуска не присваивались.

Контейнеры и сети обеих репетиций удалены, два QA-volume сохранены. Публичное размещение, systemd и реальный сертификат этим результатом не подтверждаются.
