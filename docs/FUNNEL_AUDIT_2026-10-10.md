## Вывод

Переделывать рабочую форму целиком оснований нет. Есть один подтверждённый

Сначала закрыть покрытие `/venues`, затем уточнить ошибки. Решения о сокращении

## Конкретные замечания

### 1. P2 — страницы площадок исключены из аналитики и уведомления

`frontend/src/lib/analytics.ts:28–31`: `safePath` содержит перечень разделов,
в котором нет `venues`. Это затрагивает сразу три места:

- `track` возвращает false на `/venues` и `/venues/vinni-puh`
  (`analytics.ts:54–58`), включая цели формы, контактов и галереи.
- SPA-просмотр не отправляется (`site-analytics.tsx:85–94`).
- Уведомление согласия не выводится (`site-analytics.tsx:120`).

Изолированное исполнение текущего модуля с заглушкой SDK, доменом mu56.ru
и разрешением accepted дало:

```json
{"venue":null,"venueDetail":null,"formOpenDelivered":false,"sdkCalls":0,"existingPage":"/animators"}
```

Для ранее согласившегося посетителя SDK всё ещё может инициализироваться,
но это не доказывает корректный просмотр страницы: явные hit и цели отсекаются.
Для нового посетителя нет возможности согласиться непосредственно на площадке.
Сохранение заявки не зависит от `track`, поэтому это пробел измерения,
а не установленная поломка отправки.

Рекомендация: адресно добавить публичные маршруты площадок в safePath;
сохранить исключение административных адресов и очистку query/fragment.
Дополнить существующий check_analytics проверками обоих новых адресов и
приватных параметров. После публикации отдельно проверить приём событий.

### 2. P2 — сбой расчёта может блокировать отправку без отдельной диагностики

`lead-dialog.tsx:109–118`: запрос цены для анимации/трансформера при ошибке
записывает только `quoteError`. Пока quote отсутствует, кнопка отправки
отключена (`lead-dialog.tsx:224`); посетитель видит ошибку и «Повторить расчёт»
(`lead-dialog.tsx:217`). Это разумное поведение UI, но ошибка не представлена
отдельным событием в аналитике. `submit_error` возникает только внутри submit.

По текущим целям такой уход нельзя отличить от добровольного прекращения
выбора программы. Изолированный тест тайм-аута расчёта уже проходит.

Рекомендация: добавить безопасную диагностику стадии расчёта с фиксированным
типом ошибки/стадией, не отправлять сырой message и URL. Не смешивать её с
реальной попыткой POST. Новая цель требует синхронизации кода, документа и
счётчика; расширение существующей цели тоже требует ясной семантики.
Сейчас цель не добавлялась и кабинет не менялся.

### 3. P3 — POST 403 классифицируется как ошибка данных

`lead-dialog.tsx:156`: классификация POST использует только ветки 429,
5xx и «validation» для остальных ответов. Поэтому CSRF-отказ 403 становится
`submit_error` с reason=validation и status=403. При отказе GET csrf причина
уже классифицируется как csrf (`lead-dialog.tsx:136`).
`backend/leads/views.py`, csrf_failure, действительно возвращает API 403.

Рекомендация: отдельно классифицировать известный CSRF-отказ 403; HTTP status
сохранять. Сейчас его ещё можно выделить в отчёте по status, поэтому это
замечание меньшего приоритета. Не считать все 4xx ошибками ввода пользователя:
409 означает конфликт изменённых данных уже сохранённой заявки.

## Что реализовано правильно по исходникам и локальным проверкам

- Аналитика разрешена только на mu56.ru, после accepted и готовности SDK.
  localhost и dev.mu56.ru исключены. До разрешения цели не накапливаются
  для последующей отправки задним числом.
- safeParams пропускает фиксированные параметры, публичные slugs и числа;
  имя, телефон, текст пожеланий, поисковая строка и произвольный href
  отбрасываются. В текущих вызовах track не обнаружены передачи полей заявки.
- URL цели очищен от query/fragment, внешний referrer ограничен origin.
  webvisor/clickmap/trackLinks выключены, форма имеет ym-disable-keys.
  SDK всё равно получает технические сведения браузера; это не обещание
  полностью анонимной аналитики.
- `FormJourney` различает открытие, начало, взаимодействия, попытки,
  ошибки, успех и закрытие. Начало/первое взаимодействие с полем и успех
  не дублируются в рамках одного открытия; новая попытка увеличивает attempt.
- phone_ready — достижение этапа допустимого телефона, а не гарантия его
  существования или валидности на момент последующего закрытия.
- Телефон и согласие обязательны; детали, дата, герой и имя не являются
  обязательными линейными ступенями воронки. Подробности можно свернуть,
  сохранив выбранный состав.
- Сеть и тайм-аут POST дают понятное сообщение о неопределённом результате.
  Данные остаются в форме; ключ отправки сохраняется при повторе в том же
  открытии. Закрытие заблокировано, пока busy.
- Повтор с тем же ключом и данными возвращает существующую заявку;
  изменённые данные для сохранённого ключа дают 409. У модели ключ уникален,
  сохранение обёрнуто transaction.atomic, гонка обработана через IntegrityError.
  Уведомление имеет OneToOne к заявке. Это вывод по коду и существующим тестам,
  не новый результат PostgreSQL-теста или серверной проверки.
- Закрытие и повторное открытие сбрасывает ключ. Если после потерянного
  ответа закрыть форму и создать заявку снова, дедупликация между открытиями
  не гарантируется; текущий текст предлагает повторять без закрытия и правок.
  Не расширять хранение персональных данных в браузере ради этого случая
  без доказанной необходимости.
- `report_leads` читает агрегаты с границами дней Оренбурга (UTC+5), не
  экспортирует контакты/идентификаторы и не отправляет Telegram. Тесты
  включены, статусы текущие, а не исторические — это явно отмечено.
