## 1. Сейчас — два подтверждённых дефекта формы

**P1: зависающий расчёт.** Ограничить запросы animation-quote/transformer-quote 15 секундами, затем показать понятную ошибку и кнопку повтора. При смене состава или закрытии отменять старый запрос; старый ответ не должен перезаписывать новую цену.

**P2: цена в аналитике.** Звук уже включён в API-расчёт, но повторно прибавлялся для price_band. Использовать общий итог для UI и аналитики; отдельно добавляется только фотограф. Серверные цены не менять.

Приёмка: зависший запрос завершается, повтор работает, отмена сохранена; 7000 ₽ со звуком остаётся в диапазоне 5000–9999, неизвестный тариф фотографа не становится известной суммой. **Исправления локально выполнены в этой сессии, пока не опубликованы.** Проверки `check_booking_quote.mjs` (искусственно зависший fetch, отмена, повтор, ошибки API и сумма), `check_analytics.mjs`, TypeScript, production build и diff-check прошли. Сценарный fetch использует заглушку, реальная заявка не отправлялась. Сборка сохраняет прежние предупреждения Turbopack о AVIF главной. Локальный просмотр восстановлен на 3001.

## 2. Следующий этап — повтор отправки без дубля

**Локально завершено 8 октября:** Idempotency-Key, уникальный UUID заявки, HMAC состава, повтор 200 / изменение сохранённого запроса 409, совместимость клиента без ключа и ротации ключа с fallback. В отдельной PostgreSQL-базе прошли тесты конкурентного сохранения, одна заявка/одно уведомление, независимый заказ, ошибки и CSRF. Вместе с каталогом/заявками — 120 успешных тестов. Миграция применена только к локальной базе; production не менялся. Порядок релиза — сначала миграция, затем новая форма; автоматический откат миграции не требуется.

**P2, надёжность:** если сервер сохранил заявку, но ответ потерялся, повтор должен вернуть ту же заявку и не создавать второе уведомление. Сейчас форма предупреждает о возможном сохранении; ключа повторяемой отправки на сервере нет. Это не доказательство массовых дублей.

1. Ключ одной попытки заказа; повтор с тем же ключом возвращает результат.
2. Новый независимый заказ получает новый ключ. Не объединять заявки по телефону.
3. Уникальное ограничение БД, тест одновременных повторов, проверка совместимости старых клиентов и отката.
4. Сохранить CSRF, лимиты, согласие и серверный расчёт.

Приёмка: потерянный ответ + повтор = одна заявка и одно задание Telegram; два разных заказа = две заявки. Изолированные тесты, затем отдельный согласованный релиз с миграцией. Не смешивать с небольшим frontend-релизом.

## 3. Мобильный путь к заявке

**Браузерная приёмка текущей локальной сборки:** Chrome, запрошенные 360/390 px (содержимое 345/375 px из-за скроллбара). Анимация + звук + фотограф = 9000 ₽; найден и выбран Гарри Поттер, закрытие возвращает фокус к кнопке открытия. Бамблби + азотное = 12600 ₽, выбранное шоу перенеслось в форму. Серебряное пати + второй аниматор + звук = 13800 ₽. Новогодний тариф 31 декабря 18:00 даёт 7000 ₽, неверные 19:00 блокируют отправку и показывают исправляемую ошибку. Переполнения открытых форм нет. Настоящая телефонная клавиатура и новый end-to-end POST в браузере не проверены; реальные заявки/Telegram не отправлялись. Потеря ответа проверена сценарными тестами на отдельной БД.

Проверить 360/390 px и настоящий телефон по четырём маршрутам:

- Каталог → персонаж → анимация → заявка.
- Трансформер → второй герой → шоу → расчёт.
- Пакет → состав → второй аниматор/звук → заявка.
- Новый год → формат/вечерний тариф → дата/время → заявка.

Для каждого проверить видимость цены и кнопки, длинные названия, поиск с клавиатурой, сохранение выбора при переходах, возврат фокуса, исправление ошибки. Дополнительно — увеличенный текст, работа без согласия на аналитику, слабая сеть. Настоящие заявки отправлять только по необходимости и с согласованием.

Приёмка: нет горизонтального переполнения, активный выбор и ошибка понятны, клавиатурное управление работает, введённые значения не теряются при сбое. Количество полей/шагов менять по найденной проблеме, а не по предположению.

## 4. Аналитика для решений

- Проверить доставку целей после исправления цены: открытие, начало, готовый контакт, отправка, сохранение, ошибки, уход, контакты.
- Сравнивать 7/28 дней, абсолютные числа, мобильные/desktop, источники и страницы входа. Отмечать известные тесты.
- Клик в мессенджер, сохранённая заявка и согласованный заказ — разные результаты. Использовать статусы админки для реального результата.
- Для формы смотреть этапы ухода и причины ошибок. На малой выборке фиксировать гипотезу, а не вывод.
- Отказавшиеся от Метрики отсутствуют в полной поведенческой воронке; серверные обращения не равны уникальным людям.
- Не передавать имя, телефон, комментарий или точный адрес в события. Не добавлять счётчики ради количества.

Приёмка: короткий отчёт с периодом/фильтрами: что произошло → где теряем → что меняем → как проверяем. Не сокращать форму без данных.

## 5. Индексация и поисковые страницы

**15–22 октября:** повторно открыть Google Search Console и Яндекс Вебмастер — свежесть данных, индексируемые страницы, запросы/исключения, решение по региону Оренбург. Ежедневные повторные запросы индексации не нужны.

Группы: аниматоры, трансформеры, пакеты, Дед Мороз/Снегурочка; отдельно сад/выпускной/большая группа. Сопоставлять запрос → страницу → показ → переход → заявку. При исключениях сначала искать причину, потом править.

По данным улучшать слабые заголовки, ожидания от предложения, заметность цен. Возможная косметическая задача — убрать повтор города в title там, где он уже в названии. Это не срочный дефект и не гарантия роста.

Приёмка: полезные страницы доступны роботу, нет случайных дублей, метаданные соответствуют услуге. Не создавать одинаковые районные страницы, искусственные отзывы, FAQ-разметку или llms.txt ради топа.

## 6. Локальные карточки и доверие

- Проверить Яндекс: название, оба номера, сайт, ежедневные часы 10:00–20:00, место сотрудничества и новый логотип.
- Проверить связь новой карточки с сайтом и состояние старой «больше не работает», чтобы сведения не противоречили друг другу.
- Google Business Profile: видеоподтверждение после возвращения владельца примерно через месяц. Домашний адрес не переносить в публичный сайт/технический отчёт.
- Синхронизировать факты в используемых VK/Авито/прочих профилях после проверки. Не создавать десятки новых площадок.

Приёмка: клиент видит актуальные контакты и реальный способ заказа. Изменения внешних аккаунтов — по согласованному конкретному действию.

- Проверять доступность костюмов, сезонные условия и реальные фото через штатную админку.

Приёмка: материал решает самостоятельный вопрос, содержит подтверждённые факты и помогает выбрать. Публикации «каждую неделю» без пользы не требуются.

## 8. Скорость и фотографии

- Измерять после существенных изменений: несколько прогонов, отдельно холодная/повторная загрузка.
- Смотреть LCP, CLS, отзывчивость; 90+ — желаемый лабораторный результат, но качество фото сохраняется.
- Новые uploaded-фото: размеры, формат, адаптивные варианты, lazy loading вне первого экрана, стабильный макет.
- Каталог кешировать только с понятным обновлением после админки; персональные ответы/заявки не кешировать.

Приёмка: измеримое исправление воспроизводимого узкого места и визуальная проверка. Не пересжимать весь архив ради случайного балла.

## 9. Бот и обработка заказов

- При сбое сверять заявку в админке, возраст очереди и ошибки; не повторять уже отправленные уведомления.
- Недоступность Telegram проверять изолированно: заявка сохраняется, повторы ограничены, ошибка понятна владельцу.
- Развивать существующие статусы и заметки под реальную работу. CRM и клиентского бота сейчас не строить.
- Календарь доступности — отдельный этап после описания расписания команды; заявка сама не бронирует дату.

Приёмка: заявка не теряется из-за Telegram, владелец понимает её состояние, лишних уведомлений нет.

## 10. Эксплуатация без разрастания

- Проверить объём диска после следующей выкладки; сохранять текущий и предыдущий релиз.
- Следовать принятой ротации БД/медиа, не плодить полные архивы к каждому релизу на VPS.
- Внешние резервы/восстановление перепроверять при изменении формата или проблеме; уже пройденную репетицию без причины не повторять.
- Проверять HTTPS/продление, автозапуск, диск, очередь и зависимости. Тяжёлый мониторинг для одного сайта не добавлять без необходимости.
- Учебные сайты — отдельные проекты после оценки ресурсов, не смешивать их данные/секреты с mu56.

Приёмка: работает откат кода, данные сохранены отдельно, достаточно диска, сервисы доступны.
