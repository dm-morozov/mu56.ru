# Когда покупать сервер

Сервер пока покупать не нужно. Локальная приёмка, оптимизация и подготовка
конфигурации выполняются на компьютере. Покупка имеет смысл после завершения
пунктов ниже, когда готова конкретная версия для тестового размещения.

## До покупки

- Завершить проверку на телефоне: меню, поиск героя, ввод и удаление телефона,
  расчёт состава, отправка тестовой заявки. Открытие по Wi-Fi уже подтверждено;
  оно не означает завершения всей приёмки.
- Зафиксировать принятые изменения приложения в локальной версии. Чужие
  незавершённые изменения не включать автоматически.
- Подтвердить данные для политики/согласия, получателя уведомлений и материалы
  по [PERSONAL_DATA.md](PERSONAL_DATA.md).
- Выбрать место внешних резервов. Архив на том же компьютере пока не является
  внешней копией.
- Согласовать отдельную ветку нового проекта на GitHub и тестовый адрес.
  Старые main, GitHub Pages и домен сохранять до согласованного переключения.
- Согласовать с владельцем вариант размещения, ежемесячный бюджет и стоимость
  внешних резервов. Ничего не покупать и не переключать без его указания.

## В момент выбора размещения

Проверить поддержку Linux, Django/Gunicorn, Node/Next.js и PostgreSQL,
постоянного хранения media, кеша Next.js, автоматического запуска служб,
HTTPS и резервов. Учесть ресурсы не только приложения, но и сборки/обработки
изображений. Размер оригиналов media не равен объёму загрузки браузером.
Ресурсы и тариф выбрать по актуальным условиям провайдера и замерам;
из местных Lighthouse-баллов не выводить число посетителей, которое выдержит сервер.

Сначала разместить проверенный код на отдельном тестовом адресе с отключённой
индексацией и ограниченным доступом. Затем проверить HTTPS, телефон, заявку,
доставку уведомления, перезагрузку, резервирование и восстановление. Только
после приёмки согласовать подключение основного домена.

## Подготовлено локально 6 октября 2026

В `deploy/nginx/mu56.conf` включены:

- HTTP/2 через TLS, синтаксис совместим с Nginx 1.24 в Ubuntu 24.04.
- Gzip текстовых ресурсов и Vary: Accept-Encoding. JPEG/WebP/видео повторно
  не сжимаются gzip. API и admin исключены из этого сжатия.
- Годовое immutable-кеширование только успешных ответов `/_next/static/`:
  имена файлов сборки меняются вместе с содержимым. Отсутствующие файлы не
  получают этот заголовок. HTML, API, пользовательские фото и видео не получают
  такое правило; заголовки приложения сохраняются.

Прошли `nginx -t` и 22 изолированные проверки настоящего Nginx: маршруты,
заголовки прокси, ограничения тела, CSRF-маршрут, static/media, Range видео,
HTTP→HTTPS, приватный внутренний вход, журнал без query string, gzip с
проверкой распакованного содержимого, кеширование и TLS ALPN h2.

Команда использует уже существующий локальный образ, не публикует порты и
не имеет внешней сети:

```powershell
docker run --rm --network none --mount 'type=bind,source=C:\GitHub\mu56.ru,target=/workspace,readonly' --entrypoint python3 mu56-linux-qa-afb3de0f4b-acceptance:latest /workspace/scripts/check_deploy_linux.py --nginx /usr/sbin/nginx --mime-types /etc/nginx/mime.types --skip-systemd
```

В этом контейнере нет systemd-analyze: проверки systemd явно исключены,
службы не запускались. В preflight добавлены обе службы контроля резервов;
проверен синтаксис shell. Права пользователей, реальные сертификаты,
автопродление, systemd и скорость публичной площадки остаются проверками на
выбранном сервере. Повышение Lighthouse-баллов от этой конфигурации пока
не измерено. Wi-Fi версия работает напрямую через Next.js, без этого Nginx.

Источники: [Nginx gzip](https://nginx.org/en/docs/http/ngx_http_gzip_module.html),
[Nginx HTTP/2](https://nginx.org/en/docs/http/ngx_http_v2_module.html).
Полный порядок запуска: [DEPLOYMENT.md](DEPLOYMENT.md), актуальный маршрут:
[ROADMAP.md](ROADMAP.md).
