# Задание второму чату: место на VPS mu56.ru

## Запрос владельца и границы работы

8 октября 2026 владелец сообщил: из 25 ГБ диска свободно около 7 ГБ,
контейнеров кажется слишком много. Просит выяснить причины, сократить лишнее
и не держать отдельную постоянную dev-версию. Эти цифры — сообщение владельца,
не свежий замер сервера в этом чате.

Выполнить диагностику и безопасную экономию места на существующем VPS.
Не менять Google/Яндекс, контент, цены, аналитику и интерфейс: это ведёт первый чат.
Не покупать ресурсы и не объединять все процессы в один контейнер ради количества.
Перед работой прочитать ai-context/project-overview.md, AGENTS.md,
docs/DEPLOYMENT.md, docs/DEPLOY_ACCESS.md, docs/DOCKER_DEPLOY.md, docs/BACKUPS.md
и актуальный workflow. Исторические фразы про dev/GitHub Pages сверять с сервером:
основной сайт уже mu56.ru. Секреты, env и данные заявок в отчёт не выводить.

## Что уже известно из конфигурации репозитория

deploy/docker/compose.yml задаёт проект mu56 и отдельные сервисы:

| Сервис | Назначение | Комментарий |
| --- | --- | --- |
| frontend | Next.js | Страницы сайта |
| backend | Django/Gunicorn | API, админка и заявки |
| database | PostgreSQL | Постоянные данные; удаление недопустимо |
| gateway | Внутренний Nginx | Проксирование, media и static |
| worker | Telegram | Отдельный процесс; использует тот же образ, что backend |
| storage-init | Одноразовая настройка volumes | Профиль tools; не должен постоянно работать |

Таким образом, пять рабочих контейнеров могут обслуживать ровно один сайт.
Число контейнеров не равно числу копий сайта. Backend и worker разделяют образ;
размеры общих слоёв нельзя складывать как независимые. Live-состав ещё проверить.
Системный Nginx с HTTPS вне Compose тоже может быть нужен.

Постоянные volumes: database, media, static, private-cache, next-cache.
По runbook проект на /srv/projects/mu56, резервные копии в backup-v2.
Ранее согласованы swap 2 ГБ, ежедневные дампы БД до 90 дней, три версии фото,
защитный бюджет резервов 1 ГиБ. Проверить фактическое состояние и размеры;
не считать локальную БД копией актуальных production-заявок.

## 1. Сначала инвентаризация без изменений

Использовать штатное существующее SSH-подключение. Не печатать конфигурацию
с раскрытыми env, токены, приватные ключи или полные записи заявок.
Подходящие read-only команды на Linux:

```sh
df -hT
df -i
free -h
swapon --show --bytes
docker compose ls --all
docker ps -a --size --format 'table {{.ID}}\t{{.Names}}\t{{.Status}}\t{{.Image}}\t{{.Size}}'
docker system df -v
docker image ls --digests
docker volume ls
journalctl --disk-usage
sudo du -xhd1 /var /srv /opt /home 2>/dev/null
```

Уточнять du только в крупных найденных каталогах; не сканировать файловые
системы volumes параллельно несколькими тяжёлыми проходами. Найти:

- Действующий Compose-проект, все сервисы, release/image ID, labels проектов.
- Старые контейнеры, отдельные QA/dev-проекты и их владельцев; отличить dev-домен,
  который ведёт на тот же сайт, от отдельного экземпляра приложения.
- Образы активного и предыдущего исправного релизов, старые образы, build cache.
- Архивы доставки images.tar, распакованные релизы, временные файлы и резервы.
- Docker stdout-логи, journal, кэши Next.js/оптимизации фото, apt-кэш.
- Размер БД, media и резервов; целостность/статус последнего резервирования.
- Реальный swap, системные расходы, inode; не объяснять весь диск Docker без цифр.

Выдать таблицу «категория → размер → зачем нужна → можно ли удалить».
Фактические размеры отличать от reclaimable и общих слоёв образов.

## 2. Сокращение только установленных лишних данных

До удаления записать активный релиз, используемые образы, volumes, текущий
способ отката и доступный резерв. Не создавать ещё полный многогигабайтный
архив лишь ради очистки; использовать проверенные существующие копии.

В рамках запроса владельца можно удалить точно неиспользуемые архивы доставки,
временные файлы, остановленные одноразовые контейнеры и устаревшие образы/cache,
если установлено, что они не нужны работающим сервисам или сохранённому откату.
Удалять адресно по проверенным путям/ID. Если принадлежность или назначение
неясны, сохранить объект и отдельно описать вопрос владельцу.

Обязательно сохранить активные образы и один предыдущий исправный релиз для
отката (общие слои не дублируются полностью). Устаревшие dev/QA-контейнеры
убирать только после проверки, что текущие сайт, база, media и worker их не используют.

Запрещены слепые docker system prune -a --volumes, docker volume prune,
docker compose down -v, удаление /var/lib/docker вручную и удаление данных БД/media.
Не сокращать согласованную глубину резервов без отдельного решения владельца.
Не уменьшать swap автоматически ради свободного места.

## 3. Предотвращение повторного роста

Проверить существующую очистку релизов в deploy-скрипте до добавления новой.
Если причина установлена, внести минимальный адресный механизм:

- Удалять архив доставки после успешной загрузки образов и проверки выкладки.
- Оставлять активный и предыдущий исправный релиз; удалять только образы проекта,
  которые не используются контейнерами и не входят в сохранённые релизы.
- Ограничить Docker-логи, например max-size/max-file, с оценкой необходимости
  пересоздания контейнеров; не создавать перерыв в обработке заявок без плана.
- Сохранить согласованные лимиты резервов и проверку ошибки их создания.
- Кэш изображений сокращать только при доказанном росте: полная очистка ухудшит
  первые загрузки на 1 vCPU. Не ухудшать фото ради цифр.

Не вводить ещё одну инфраструктуру или постоянный сервис мониторинга без
необходимости. Не делать автоматические глобальные prune по расписанию.
Рабочие изменения первого чата сохранить; не публиковать чужие правки автоматически.

## 4. Приёмка и результат

После очистки сравнить df/docker system df с исходными значениями; назвать
освобождённый объём и оставшийся запас. Проверить health/status всех необходимых
сервисов, HTTPS mu56.ru, главную/каталог/API/админку и очередь Telegram без раскрытия
заявок. Не отправлять новую заявку или повторять исторические уведомления для теста.
Если требуется реальная тестовая отправка, согласовать её отдельно.

Подготовить docs/SERVER_STORAGE_AUDIT_2026-10-08.md:

1. Фактическая причина расхода диска с размерами.
2. Назначение каждого оставленного контейнера, наличие/отсутствие второго экземпляра.
3. Что удалено, сколько освобождено, что сохранено для отката и резервирования.
4. Как предотвращён повторный рост и какие проверки прошли.
5. Оставшиеся вопросы/риски и точный список изменённых файлов.

Цель — достаточный устойчивый запас на диске и работающий сайт с ботом,
а не произвольное число «один контейнер» или максимальный объём любой ценой.
