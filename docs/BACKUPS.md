# Локальная резервная копия и проверка восстановления

Запуск из корня проекта:

```powershell
& .\scripts\dev_postgres.ps1 Load
.\.venv\Scripts\python.exe scripts/backup_local.py
```

Скрипт принимает только отдельный локальный PostgreSQL mu56 на 127.0.0.1:55456. Создаёт новую папку .local/backups с уникальным именем: database.dump, source.zip, media.zip и manifest.json. .local исключена из Git. Копия базы содержит заявки и пользователей админки: хранить её приватно.

Код включает backend, frontend, scripts, docs, deploy, .github (если есть) и корневые Markdown-файлы. Зависимости, сборки, SQLite, заполненные .env, ключи/сертификаты, отдельные дампы SQL, docs/internal, кластер PostgreSQL и секреты .local не копируются; env-шаблоны сохраняются. Медиа Django идут отдельным архивом; публичные ассеты frontend входят в код. Исходный буклет, исходный тяжёлый архив scraper и старый вложенный репозиторий mu56 не входят: это резервная копия текущего приложения, не всего исходного архива владельца.

Дамп и эталонные количества строк читаются из одного экспортированного PostgreSQL-снимка в транзакции REPEATABLE READ READ ONLY. Новые заявки могут продолжать поступать: они попадут в следующую копию. После дампа скрипт создаёт новую базу mu56_restore_<случайный суффикс>, восстанавливает схему и данные без перезаписи mu56 и сравнивает состав таблиц и число строк каждой публичной таблицы со снимком. Zip проверяются чтением и SHA-256 каждого файла; контрольные суммы архивов и таблицы сохраняются в manifest.json. Эти проверки не отключаются при запуске Python с флагом `-O`.

Снимок PostgreSQL не синхронизирует файлы на диске. Во время копирования не менять каталог, фотографии и исходники: для согласованной копии базы и медиа нужен период без таких изменений. Сверка количества строк не является побайтовым сравнением содержимого таблиц.

Восстановленная база остаётся для осмотра. Приложение и Telegram worker к ней не подключаются; запуск обработчика на копии с очередью недопустим без отдельного решения. Скрипт не удаляет старые копии или базы.

## Внешнее хранение и production

### Серверная копия данных — 5 октября 2026

`backup_site` работает через настройки Django на Windows/Linux. Создаёт уникальную папку с `database.dump`, `media.zip`, `manifest.json`; пароль берёт из окружения, не из аргументов. Дамп и количества строк публичных таблиц читаются из одного экспортированного снимка PostgreSQL. Все media проверяются чтением архива и SHA-256; отсутствие привязанного фото прерывает копию.

Это полная приватная копия данных: содержит пользователей, заявки и очередь Telegram. Код, `frontend/public`, static/cache, серверные настройки и секреты не входят. Для восстановления сохранять commit релиза Git, зависимости, публичные ассеты и секреты отдельно. До первого релиза нужна актуальная полная локальная копия `backup_local.py`; грязный checkout не является воспроизводимым Git-релизом.

```powershell
& .\scripts\dev_postgres.ps1 Load
.\.venv\Scripts\python.exe backend/manage.py backup_site .local/server-backups --pg-bin 'C:\Program Files\PostgreSQL\18\bin'
```

На будущем Linux-сервере создать `/srv/mu56/backups` владельцем `mu56:mu56` с правами 0700, вне публичных путей. Установить клиент PostgreSQL 18. Ручной запуск:

```bash
sh /srv/mu56/current/deploy/manage.sh backup_site /srv/mu56/backups
```

Подготовлены `mu56-backup.service` и `mu56-backup.timer`: ежедневно в 03:00 UTC с задержкой до 10 минут, пропущенный запуск выполняется после включения сервера. Umask 0077, запись только в папку резервов. Шаблоны проверены systemd, таймер не включён. После серверной репетиции и выбора внешнего хранения: установить оба файла, выполнить `sudo systemctl enable --now mu56-backup.timer`, проверить `systemctl list-timers`, журнал сервиса и законченный manifest.

Копия логическая: не включает роли PostgreSQL и не обеспечивает восстановление к произвольной секунде. Это начальный этап для небольшого сайта; допустимую потерю заявок между копиями согласовать до публикации и при необходимости добавить WAL/PITR. Во время копирования не удалять/заменять фото; заявки могут поступать. [Форматы и ограничения pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html).

`archives_verified: true` означает проверку архивов, `restore_verified: false` — команда не восстанавливала базу. Отдельная репетиция: новая пустая база, `pg_restore --exit-on-error --no-owner --no-acl` туда, сравнение таблиц/количеств со снимком и проверка фото. Не применять `--clean` к рабочей базе, не запускать migrate перед восстановлением полного дампа, не включать worker на копии.

Проверено `scripts/check_data_transfer.py`: `.local/data-transfer-qa-a209065ab7/backups/20261005T090951Z_5a5857c2`, база `mu56_restore_23a0036e3638`. Восстановлены 22 таблицы с совпавшими количествами строк, media проверены по хешам. Отчёт — `verification.json` родительской папки. Это Windows/PostgreSQL-репетиция, не восстановление Linux-сервера.

Автоматического удаления копий нет. До публикации согласовать срок хранения, контроль свободного места, уведомление о сбое и внешний зашифрованный носитель. Внешние загрузки пока не настроены.

Дополнительная копия после подготовки серверного запуска (5 октября по времени владельца): `.local/backups/20261004T214221Z_4dea1c`, база проверки `mu56_restore_6a5889741726`. Восстановлены 22 таблицы; проверены 341 файл проекта и 352 файла media. Архив включает все 10 файлов deploy, production-модуль и два Linux-стенда проверки. Заполненных env-файлов и ключей в source.zip нет; оба env-шаблона и deploy/requirements.txt присутствуют. Дампы и исходный архив находятся только локально.

Сохранить вторую защищённую копию на другом носителе: копия на том же диске не защищает от его потери. Место внешнего хранения и расписание согласуются отдельно; облачные загрузки не выполнялись. Секреты восстанавливаются отдельно из безопасного хранилища владельца. Перед production потребуется процедура согласованного копирования базы и медиа во время загрузок, срок хранения и проверка восстановления на отдельном окружении.

## Контроль резервных копий — 6 октября 2026

`check_backup` только читает последнюю папку формата backup_site: проверяет завершённый manifest, возраст (по умолчанию до 36 часов), SHA-256 дампа и ZIP, список/хеши файлов внутри media.zip и свободное место (по умолчанию минимум 1 ГиБ). Незавершённая более новая папка вызывает ошибку: проверка не подменяет её старой удачной копией. Ненулевой код означает сбой; копии не удаляются. Проверка хешей не является восстановлением PostgreSQL.

```powershell
.\.venv\Scripts\python.exe backend/manage.py check_backup .local/data-backups
```

Сервер: `mu56-backup.service` после создания копии выполняет эту же проверку. Дополнительные `mu56-backup-check.service/timer` проверяют свежесть каждые четыре часа (00/04/08/12/16/20 UTC, до 5 минут случайной задержки). Устанавливать вместе с backup timer только после настройки хранения и проверки восстановления. До активации проверить свежую копию вручную. Ошибка видна в failed-состоянии и journal systemd; сообщения владельцу пока не подключены. Команды контроля: `systemctl status mu56-backup.service mu56-backup-check.service`, `journalctl -u mu56-backup-check.service --since today`. Шаблоны не установлены и не включены.

Свежая приватная копия данных: `.local/data-backups/20261006T074220Z_9fb8c7b4`, 464 файла медиа, проверка прошла. Код и секреты в backup_site не входят. Для ссылок базы на ранее удалённые публичные фотографии поддержан явный `backup_site --archived-media-root <приватная папка>`. Только отсутствующие файлы читаются из этого источника и записываются в приватный ZIP. Файлы на сайт не возвращаются, история базы не переписывается. По умолчанию при отсутствии любого нужного файла резервирование останавливается.

Внешняя копия остаётся неподключённой: нужно выбрать носитель/хранилище и приватный способ передачи. Перед использованием проверить хеши в месте назначения и провести восстановление в изолированной базе, без Telegram worker. Хранилище содержит заявки и аккаунты — доступ только владельцу. Предварительная схема хранения для обсуждения: 14 ежедневных и 3 ежемесячные копии; автоматическое удаление пока не реализовано и не выполняется. Незавершённые папки не считать копиями. Уведомления о сбоях и окончательный срок хранения настраиваются при размещении.
