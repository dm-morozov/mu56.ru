# Проверки, выкладка и откат

## До появления сервера

Новый сайт развивается в отдельной ветке `local/release-20261006`.
Прежняя `main` и GitHub Pages сохраняются. Истории проектов самостоятельные;
не делать force push и не объединять их ради публикации нового приложения.

GitHub Actions запускает `.github/workflows/ci.yml` при push и pull request.
Результат проверки относится к конкретному SHA. Для релиза нужен успешный
прогон именно выбранного commit, а не более старой версии.
Сборка выполняется с отдельной базой, без рабочих данных и Telegram.

Изменения дальше готовить в `feat/<тема>` или `fix/<тема>` от ветки нового
приложения, проверять через pull request в эту же линию истории. После первого
успешного CI можно выбрать постоянную ветку нового приложения и включить для
неё обязательные проверки. Не менять правила старой main автоматически.

## После выбора сервера

1. Согласовать тестовый адрес и основной сервер; создать отдельный deployment
   workflow с ручным `workflow_dispatch`. CI сам по себе ничего не выкладывает.
2. Настроить ограниченный SSH-доступ и GitHub environments для тестовой и
   основной площадок. Рабочие секреты хранятся на сервере; deploy-ключ задаётся
   через Secrets. Не использовать личный SSH-ключ владельца для CI.
3. Выкладывать только полный SHA с успешным CI. Подготовить новый каталог
   `/srv/mu56/releases/<sha>`, зависимости и сборку до переключения `current`.
4. На тестовом адресе проверить страницы, фотографии, цены, форму и
   согласованную доставку уведомления. Индексация выключена. Подтвердить
   перезапуск служб, резервирование и изолированное восстановление.
5. Основную выкладку запускать вручную после приёмки. Перед миграциями —
   свежий проверенный резерв. Согласованно остановить worker, при необходимости
   приём заявок, применить миграции, атомарно переключить `current`, перезапустить
   службы, выполнить HTTP-проверки и вернуть worker после успеха.

До выбора сервера deployment workflow не создан: адрес, SSH-пользователь,
права и способ перезапуска ещё не определены. Сейчас не нужен фиктивный job,
который будет «успешно» выкладывать без реальной площадки.

## Откат

- Сохранить предыдущий каталог релиза, его SHA, зависимости и статику.
- Перед обновлением проверить совместимость старого кода с новой схемой БД.
- Если переключение/HTTP-проверка неудачны, остановить worker и вернуть ссылку
  `current` на предыдущий готовый релиз; перезапустить и повторить проверки.
- Не выполнять автоматический откат миграций и восстановление дампа.
  Восстановление БД требует отдельного решения и сохранения новых заявок,
  поступивших после резервной копии. Проверить очередь перед запуском worker.
- После успешной выкладки записать SHA, время, результат проверки и предыдущий
  SHA. Серверная репетиция должна подтвердить и выкладку, и возврат кода.
