Дополнение от 6 октября: локально проверены HTTP/2, сжатие и кеширование
файлов сборки. Сервер покупать пока не нужно; критерии и результаты проверок:

Статус на 5 октября 2026: шаблоны и production-настройки подготовлены и проверены локально. Публичный сервер, DNS и действующий сайт не менялись. Файлы в `deploy/` предназначены для отдельного Linux-сервера, а не для обычного Windows-терминала.

## Архитектура

Публичный вход — Nginx с HTTPS. Он передаёт `/api/` и `/admin/` в Gunicorn/Django на `127.0.0.1:8000`, остальные страницы — Next.js на `127.0.0.1:3000`. `/static/` и `/uploads/` Nginx читает с диска. PostgreSQL слушает только локальный адрес; Telegram worker работает отдельной службой с той же базой.

Next.js запрашивает каталог и media через **внутренний Nginx на 127.0.0.1:8081**. Тот выставляет HTTPS-признак и правильный Host для Django, поэтому каталог не попадает в цикл перенаправлений. Внутренний вход разрешает только чтение API и медиа: POST и админка закрыты. Клиентская форма отправляется через публичный HTTPS-вход непосредственно в Django.

Nginx перезаписывает `X-Forwarded-Proto` и `X-Forwarded-For`, а не доверяет значениям клиента. Gunicorn слушает loopback и доверяет только этому адресу. Django `config.production` использует один доверенный прокси. Эта схема требует закрытых портов 3000, 8000, 8081 и PostgreSQL; перед ней пока не предполагается CDN или дополнительный балансировщик.

## Файлы

- `backend/config/production.py` — обязательные параметры, HTTPS/cookies, постоянные пути и общий файловый кеш лимита заявок.
- `deploy/requirements.txt` — зависимости Django и закреплённый Gunicorn 26.2.0.
- `deploy/gunicorn.conf.py` — два рабочих процесса, по два потока и таймауты. Число процессов уточняется после выбора ресурсов и измерения нагрузки.
- `deploy/django.env.example` и `deploy/frontend.env.example` — **раздельные** шаблоны окружения. Пароль базы и токен бота не передаются Next.js.
- `deploy/systemd/` — службы backend, frontend и Telegram с автоперезапуском, отдельным пользователем и ограничением записи.
- `deploy/nginx/mu56.conf` — HTTPS, маршруты, статика/media, внутренний вход и журнал без query string и тела формы.
- `deploy/manage.sh` — команды Django от пользователя приложения. Секретный environment-файл читает systemd, а не shell.
- `deploy/preflight.sh` — проверки подготовленного сервера; службы не включает и не перезапускает.

Production не стартует с DEBUG, пустым или коротким ключом, неизвестными параметрами БД, wildcard-хостом, HTTP-источником CSRF или пересекающимися путями static/media/private cache. Текст и версия согласия берутся из frontend/src/lib/lead-consent.json; до публикации выполнить уточнения из docs/PERSONAL_DATA.md.

## Целевая среда

Ubuntu 24.04 LTS, Python 3.12, Node.js 24 LTS, pnpm 11.19.0, PostgreSQL 18 и Nginx. Node.js 24 выбран как LTS; локальная версия — 24.18.0. Актуальные security patches runtime проверяем при подготовке сервера, а установленные версии фиксируем в записи релиза. [Таблица поддержки Node.js](https://nodejs.org/en/about/previous-releases).

Служба frontend предполагает Node в `/usr/bin/node`: перед установкой проверить `command -v node` и при необходимости поправить ExecStart. Сборка использует существующий `frontend/pnpm-lock.yaml` с `--frozen-lockfile`. Не копировать Windows node_modules или .venv на Linux.

## Каталоги и права

```text
/srv/mu56/releases/<commit-sha>/   код, .venv, node_modules и .next
/srv/mu56/current                 ссылка на выбранный готовый релиз
/srv/mu56/shared/media            загруженные фотографии и видео
/srv/mu56/shared/static           результат collectstatic
/srv/mu56/shared/private-cache    приватный общий кеш Django
/srv/mu56/shared/next-cache       кеш Next.js и оптимизированных фото
/srv/mu56/backups                 приватные полные копии данных, mu56:mu56 0700
/etc/mu56/django.env              секреты Django/БД/Telegram, root:root 0600
/etc/mu56/frontend.env            настройки frontend, root:root 0600
```

Пользователь `mu56` — системный пользователь без интерактивного входа. Каталоги media/static доступны ему на запись и Nginx на чтение: например, mu56:mu56 0750, а `www-data` входит в группу mu56. Private cache и Next cache — mu56:mu56 0700. Private cache не размещать внутри media/static и не публиковать через Nginx. Все каталоги создать **до** запуска служб: systemd проверяет разрешённые пути записи.

После сборки в каждом новом релизе заменить `.next/cache` ссылкой на `/srv/mu56/shared/next-cache`. Исходный кеш сборки можно переместить в `.next/cache-build` внутри того же релиза. Preflight проверяет наличие ссылки. Загрузки Django при обновлении не переносятся и не удаляются: MEDIA_ROOT всегда указывает в shared.

## Подготовка первого релиза — только на будущем сервере

1. Подготовить пакеты и отдельного пользователя/базу PostgreSQL. Пользователь приложения не должен быть superuser или иметь доступ к чужим базам. PostgreSQL не открывать в Интернет.
2. Разместить **проверенный commit** в новом releases-каталоге, создать Linux .venv и установить `pip install -r deploy/requirements.txt`. Установить frontend с `pnpm --dir frontend install --frozen-lockfile`.
3. Скопировать примеры окружения в `/etc/mu56/` с root:root 0600 и заполнить через `sudoedit`. Случайный ключ Django — не менее 50 символов. Токен и chat ID владелец вводит локально; `.local/telegram.json` на сервер не переносится.
4. Собирать frontend от mu56, с окружением **того же frontend.env**, который будет читать служба. BACKEND_ORIGIN участвует в Next rewrites: после его изменения нужна новая сборка, одного перезапуска недостаточно. Для тестового размещения `SITE_INDEXING_ENABLED=false`.
5. Подключить постоянные media/cache каталоги и указать current на готовый релиз. Применить миграции и collectstatic. Наполнение каталога и перенос актуальных фото/видео — отдельная операция; тестовые заявки и очередь из локальной базы не переносить автоматически.
6. Установить четыре service-файла и один timer-файл в `/etc/systemd/system/`, выполнить `sudo systemctl daemon-reload`. Таймер включается отдельно после репетиции восстановления и выбора внешнего хранения. Nginx-файл включить один раз в контекст http; проверить отсутствие конфликтов с default site.
7. Сначала использовать согласованный тестовый адрес и его сертификат. Шаблоны используют mu56.ru: другой адрес заменить согласованно в Nginx, пути сертификата, ALLOWED_HOSTS, CSRF origins и SITE_URL. Публичный mu56.ru до приёмки не переключать. `noindex` не закрывает площадку: предусмотреть ограничение доступа.

Сборку можно запускать через systemd-run, чтобы он прочитал frontend.env. Пример для уже подготовленного current:

```bash
sudo systemd-run --wait --pipe --collect \
  --property=User=mu56 --property=Group=mu56 \
  --property=WorkingDirectory=/srv/mu56/current/frontend \
  --property=EnvironmentFile=/etc/mu56/frontend.env \
  "$(command -v pnpm)" build
```

Первичная миграция, импорт каталога в новую базу (до создания админки), статика и проверки. Пакет заранее передать приватно по [DATA_TRANSFER.md](DATA_TRANSFER.md); папку backups создать с правами 0700. Скопировать в systemd четыре service-файла и один timer-файл, но timer пока не включать.

```bash
sh /srv/mu56/current/deploy/manage.sh migrate
sh /srv/mu56/current/deploy/manage.sh import_catalog /srv/mu56/import/catalog-release-01 --replace-migration-defaults
sh /srv/mu56/current/deploy/manage.sh createsuperuser
sh /srv/mu56/current/deploy/manage.sh collectstatic --noinput
sh /srv/mu56/current/deploy/preflight.sh
sudo systemctl enable --now mu56-backend mu56-frontend
```

Telegram включить после проверки получателя, каталога и очереди: в django.env поставить `TELEGRAM_ENABLED=1`, токен и private chat ID, перезапустить Django, выполнить `test_telegram`, затем `sudo systemctl enable --now mu56-telegram`. Первое сообщение — проверка связи без данных клиента. Worker начинает отправлять **уже ожидающие** уведомления: перед включением проверить их в админке.

Команды приведены для будущего сервера; в текущей проверке службы не устанавливались и не включались.

## Лимиты и HTTPS

Заявки имеют лимит Django 10/час на адрес клиента. Файловый кеш общий для двух Gunicorn-процессов; DRF throttling использует неатомарные операции и не даёт строгой гарантии при одновременных запросах. Nginx дополнительно ограничивает endpoint заявки до 10 запросов/минуту с коротким burst. Форма принимает не более 64 KiB; для загрузки медиа админкой разрешено 32 MiB. [Ограничения DRF throttling](https://www.django-rest-framework.org/api-guide/throttling/).

HSTS включён на час для текущего хоста. Два предупреждения `check --deploy` — W005 и W021 — оставлены видимыми: includeSubDomains и preload выключены до решения по остальным поддоменам. Preflight останавливается при ошибках; предупреждения не скрываются. [Настройки доверенного HTTPS-прокси Django](https://docs.djangoproject.com/en/5.2/ref/settings/#secure-proxy-ssl-header).

## Обновление и откат

Готовить новый релиз отдельно от current: установить зависимости, собрать с правильным окружением, проверить, записать commit и версии runtime. Перед миграциями нужна проверенная копия БД и media; команда backup_site и локальная репетиция готовы, внешний носитель и серверная репетиция остаются. Инструкция: [BACKUPS.md](BACKUPS.md). import_catalog предназначен только для первого запуска в пустой базе, при обновлениях его не повторять.

При переключении остановить worker, при необходимости закрыть приём заявок на обслуживание, применить миграции и статику, атомарно переключить current, перезапустить backend/frontend и проверить страницы/API/форму. Затем вернуть worker. Сохранять предыдущий релиз и его статику до завершения приёмки.

Откат current возвращает код, но не схему базы. Проверить совместимость предыдущего кода с новыми миграциями до выкладки. Если нужно восстановление базы, оно выполняется с остановленными приложением и worker после отдельного решения: новые заявки после времени копии потребуют сохранения. Не запускать worker на восстановленной копии без проверки очереди.

## Дополнение: контроль резервов

В комплект входят также mu56-backup-check.service и mu56-backup-check.timer (всего 7 unit-файлов). Установить шаблоны при размещении; активировать оба backup timer только после настройки приватного хранения, свежей копии и восстановления. Резервирование автоматически проверяет созданный архив через ExecStartPost; отдельный таймер выявляет отсутствие новых копий. Ненулевой код переводит службу в failed, но не отправляет уведомления сам по себе. Внешнее хранилище, удалённый контроль и доставка уведомлений пока требуют настройки. Подробнее BACKUPS.md.
